ZK proof가 되는 구조

ZKProofport는 인증 데이터를 발급하는 계층과 이를 사용하는 dApp 사이에서 필요한 사실만 영지식 증명으로 전달합니다. dApp은 원본 인증 데이터를 받거나 보관할 필요가 없습니다.

MVP 확인 구현 자료

01 / PROBLEM

Dojang 데이터를 지갑 주소로 직접 조회할 때

Dojang은 신뢰할 수 있는 오프체인 정보를 온체인 인증 데이터로 연결합니다. 하지만 dApp이 인증 데이터가 발급된 지갑을 직접 확인하면 해당 지갑의 이용 기록과 인증 상태가 연결될 수 있습니다. Verified Balance처럼 값이 포함된 정보는 서비스가 실제로 필요한 범위보다 많은 내용을 보여줄 수도 있습니다.

ZKProofport는 Dojang에서 발급된 신뢰를 그대로 활용하면서, dApp에는 정책 판단에 필요한 결과만 전달합니다.

  1. 01dApp이 필요한 검증 항목과 서비스별 scope를 요청합니다.
  2. 02사용자 기기에서 지갑 소유권과 attestation의 유효성을 확인합니다.
  3. 03Noir 회로가 private inputs를 사용해 UltraHonk proof를 생성합니다.
  4. 04GIWA의 verifier가 proof와 public inputs만으로 결과를 확인합니다.

04 / CIRCUIT

GIWA attestation 검증 회로

  • 01사용자의 public key에서 주소를 유도하고 지갑 서명을 검증합니다.
  • 02attestation transaction을 파싱하고 허용된 발급자의 서명을 확인합니다.
  • 03transaction의 대상 컨트랙트와 호출 데이터가 증명 대상 지갑과 일치하는지 확인합니다.
  • 04사용자와 서비스 scope에 묶인 nullifier를 계산해 서비스 간 추적과 중복 사용을 줄입니다.

06 / BOUNDARY

Production 단계: 공식 Dojang 데이터 연동

현재 PoC는 Dojang 발급 이후의 ZK 증명 파이프라인을 검증합니다. 공식 Dojang의 Verified Address는 사용자가 KYC를 완료한 뒤 업비트가 발급하는 운영 데이터입니다. PoC에서는 발급 단계에 테스트 attester를 사용하고, 회로·모바일 증명·verifier 흐름을 구현했습니다. Production 단계에서 발급자 주소, schema와 정책을 공식 Dojang 데이터에 맞춰 연결합니다.

07 / ROADMAP

GIWA Wallet 네이티브 통합 로드맵

초기에는 독립 앱과 SDK로 빠르게 dApp 연동을 시작합니다. 공식 Dojang 데이터를 연결한 뒤에는 증명 요청·동의·생성을 GIWA Wallet 안에 통합합니다. dApp은 같은 요청 규격을 유지하면서 Verified Address, Balance, Code 등 새로운 검증 회로를 계속 추가할 수 있습니다.
